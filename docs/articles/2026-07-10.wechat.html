今天这条 GitHub Trending Daily，不是一个普通提示词仓库，而是一套给 AI 编程代理使用的“工程习惯包”。它提醒我们：真正让 AI 变强的，往往不是一句神奇咒语，而是把高手的工作流固化成可重复执行的步骤。



这个项目叫 addyosmani/agent-skills，作者把它定义为 Production-grade engineering skills for AI coding agents，也就是“面向生产级 AI 编程代理的工程技能”。

它的核心思想很简单：高级工程师写软件时，不只是写代码。他们会先澄清需求、拆解任务、逐步实现、写测试、做代码审查、检查性能，最后再发布。这个仓库把这些流程、质量门槛和最佳实践，打包成 AI Agent 可以稳定遵循的 skills。

换句话说，它不是让 AI “更会聊天”，而是让 AI 在开发全流程里更像一个有纪律的工程搭档。



仓库里最值得借鉴的是 8 个 slash commands，它们对应软件开发的完整生命周期：/spec 定义要做什么，/plan 规划怎么做，/build 增量构建，/test 证明它能工作，/review 合并前审查，/webperf 审计网页性能，/code-simplify 简化代码，/ship 发布到生产环境。

它背后的原则更重要：Spec before code，先规格，后代码；Small, atomic tasks，任务要小而原子；Tests are proof，测试就是证据；Measure before you optimize，优化前先测量；Clarity over cleverness，清晰胜过炫技。

这套顺序同样适用于写文章、做课程、搭建知识库、准备英文演讲，甚至训练自己的 AI 提示词。



如果你经常觉得 AI 输出“看起来很努力，但不够靠谱”，可以直接借用这个项目的六步工作流：Define → Plan → Build → Verify → Review → Ship。对应中文就是：定义目标、拆解计划、逐步生成、验证结果、审查质量、交付发布。

可直接复制这个提示词模式：你现在不是直接给答案，而是按一个生产级工作流协助我完成任务。任务是【填写任务】，使用场景是【填写场景】，成功标准是【填写标准】。请依次执行 Define 澄清目标、边界和风险，Plan 拆成小而独立的步骤，Build 一次完成一个切片，Verify 说明验证方法，Review 从质量和用户价值角度审查，最后 Ship 给出可直接使用的版本。如果信息不足，请一次只问我一个最关键的问题。

这个模板的关键，是阻止 AI 直接进入“生成答案”模式。你是在要求它先建立规格，再进入执行。



很多提示词的问题，是它只表达愿望：帮我写得更好、帮我分析一下、帮我优化一下。但高级提示词更像流程：先问什么，后做什么；每一步的输出是什么；怎样判断完成；哪里需要暂停确认。

比如写英文邮件时，不要只说“帮我润色”，可以改成：先判断语气是否适合收件人，再检查表达是否自然，再压缩冗余句子，最后给出英文版本和中文修改说明。这就是把“润色”变成了一个可执行的 skill。

今天的英文学习动作：选 3 个表达改写到自己的工作场景里。比如把 Spec before code 改成 Outline before writing，写作前先列大纲；把 Measure before you optimize 改成 Diagnose before you rewrite，重写前先诊断。



addyosmani/agent-skills 值得关注，不是因为它提供了某个神奇命令，而是因为它把“资深工程师如何控制质量”翻译成了 AI Agent 能执行的结构。

未来我们使用 AI 的差距，很可能不在于谁知道更多工具，而在于谁更会把自己的工作方法编码成流程、检查表和可复用提示词。
