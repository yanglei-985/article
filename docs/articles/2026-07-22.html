今天这条 GitHub Trending 不是一个“又能帮你写代码”的工具，而是一个更底层的问题：当 AI 读代码时，它到底该读多少？

很多人用 Cursor、Claude Code、Codex 或 Gemini CLI 做代码审查时，都会遇到同一个隐性成本：AI 为了理解一个改动，反复扫描大量文件。上下文窗口被占满，token 被烧掉，回答还不一定更准。code-review-graph 试图解决的就是这个问题：先给代码库建立一张本地结构图，再让 AI 只读取真正相关的部分。



它是什么：给代码库做一张“结构地图”。code-review-graph 是一个 local-first 的代码智能图谱工具，支持 MCP 和命令行。它会用 Tree-sitter 解析你的代码库，把函数、类、导入关系等结构变成图中的节点，把调用、继承、测试覆盖等关系变成边。

这张图会持久保存在本地。之后，当你让 AI 做 review 或理解大仓库时，它不需要重新“通读”整个项目，而是可以通过图谱查询到最小必要上下文：哪些文件被改了，哪些函数会受影响，哪些调用方、依赖方、测试可能相关。

它的核心口号很直接：Stop burning tokens. Start reviewing smarter. 别再浪费 token，开始更聪明地审查代码。



关键思路：不是让 AI 更努力，而是让上下文更精确。这类工具真正值得关注的地方，不在于它又接入了哪个模型，而在于它改变了我们使用 AI 编程工具的方式。

过去的常见做法是：把问题丢给 AI，让它自己在项目里找线索。问题是，大模型并不知道哪些文件重要，哪些只是噪音。于是它可能读取大量代码，既慢又贵，还容易在上下文里迷路。

code-review-graph 的做法更像“先建索引，再提问”。它把代码库转成结构化图谱，支持变更追踪和增量更新。文件变更后，它可以通过调用链、依赖关系和测试关系分析这次改动的 blast radius，也就是“影响半径”。AI 只需要围绕这个影响半径阅读，而不是扫描整个仓库。



快速上手：三步建立代码审查图。官方给出的快速开始非常简单：pip install code-review-graph，或使用 pipx install code-review-graph；然后运行 code-review-graph install 和 code-review-graph build。

install 会自动检测你本机支持的 AI 编程工具，并写入对应的 MCP 配置；也会在支持的平台中安装 hooks、skills，并向平台规则中注入与图谱相关的指令。安装后需要重启编辑器或工具。

它支持按平台单独配置，例如 Cursor、Claude Code、Codex、Gemini CLI、Kiro、GitHub Copilot、CodeBuddy Code 等。工具要求 Python 3.10+。官方示例中，500 个文件的项目初次构建大约需要 10 秒，之后可通过 watch mode 或 hooks 自动更新。



AI习语视角：这其实是一种“上下文工程”。我们经常谈 prompt engineering，但在代码任务里，更重要的往往是 context engineering：不是把提示词写得越来越长，而是把 AI 需要看的材料组织得更准。

可直接复制的提示词：请基于 code-review-graph 的代码图谱审查本次改动。请先识别本次变更的 blast radius：被修改的函数、类、模块；直接调用方和间接调用方；依赖该变更的文件；可能受影响的测试。然后只阅读与上述影响半径相关的文件，不要扫描整个仓库。请输出：高风险问题、中风险问题、需要补充的测试、可以忽略的非问题，以及建议下一步修改的最小补丁方向。

这个提示词里最值得学习的英文表达是 blast radius。它原本常用于工程和安全语境，意思是一次故障、攻击或改动可能波及的范围。放到代码审查中，就是“这个改动会影响哪里”。



一句话总结：code-review-graph 不是替你写代码的 AI，而是替 AI 准备更好的阅读路径。它提醒我们：高质量 AI 输出，往往不是来自更大的模型，而是来自更干净、更相关、更结构化的上下文。

pipx install code-review-graph

## 可操作工作流：用“影响半径”提示词做代码审查

如果你已经使用支持 `MCP` 的 AI 编程工具，可以试试下面这个工作流：

1. 先在项目中安装并构建 `code-review-graph`。
2. 每次提交前，让 AI 基于代码图谱找出本次改动的影响半径。
3. 再要求 AI 只围绕相关调用方、依赖方和测试文件做审查。
4. 最后让 AI 输出“必须修改 / 建议修改 / 可忽略”的分级结论。

可直接复制的提示词：

```text
请基于 code-review-graph 的代码图谱审查本次改动。

请先识别本次变更的 blast radius：
- 被修改的函数、类、模块
- 直接调用方和间接调用方
- 依赖该变更的文件
- 可能受影响的测试

然后只阅读与上述影响半径相关的文件，不要扫描整个仓库。

请输出：
1. 高风险问题：可能导致错误、回归或安全问题
2. 中风险问题：设计、可维护性或边界条件问题
3. 需要补充的测试
4. 可以忽略的非问题
5. 建议下一步修改的最小补丁方向
```

这个提示词里最值得学习的英文表达是 `blast radius`。它原本常用于工程和安全语境，意思是一次故障、攻击或改动可能波及的范围。放到代码审查中，就是“这个改动会影响哪里”。学会这个表达，也能帮你更准确地和英文技术资料对齐。
